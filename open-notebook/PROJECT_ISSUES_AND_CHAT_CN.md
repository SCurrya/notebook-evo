# 项目问题报告与聊天记录摘要（中文）

日期：2026-06-26

## 结论先说

当前项目仍然不算“稳定可交付”。

原因不是单一 bug，而是几条线同时存在问题：

1. 用户侧仍然感知为“不可用”。
2. 之前的修复结论和真实体验之间存在不一致。
3. 代码库处于非常复杂的 dirty worktree，历史并行改动很多，容易让人误判修复是否真的生效。
4. UI、API Key、来源、笔记本、Studio、Transformations 等页面虽然已经动过，但还需要统一验证和回归。

这份文档的目的，是把当前已知问题和我们这轮对话的关键过程整理出来，方便你换新的 IDE 继续接手。

## 当前已知问题

### 1) 用户仍然打不开或用不了应用

- 用户反馈是明确的“还是用不了”。
- 这说明之前的修复至少没有达到“用户体感可用”的标准。
- 即使某些接口已经通了，只要用户主路径还卡住，整体仍然算失败。

### 2) 之前的“修好”与真实状态不一致

- 我们一度把 EXE、API、模型同步、默认分配都记录成完成。
- 但从你后续反馈来看，真实体验并没有达到可用。
- 这意味着：
  - 要么某些验证只覆盖了局部接口，没有覆盖完整用户路径；
  - 要么运行环境、缓存、旧进程、旧入口、旧快捷方式仍在干扰；
  - 要么页面和后端接口的“表面可用”并不等于“功能可用”。

### 3) 冷启动链路虽然已补强，但仍需要继续实机确认

- 我们做过 `health` 探针和 API 启动逻辑的修正。
- 但用户层面仍然报告“打不开”。
- 这通常意味着还需要继续排查：
  - 启动后实际展示的窗口是否正确
  - 前端是否能拿到正确 API 地址
  - 是否存在旧进程残留
  - 是否存在本地缓存/浏览器缓存/桌面快捷方式仍指向旧产物

### 4) 模型、API Key、来源、笔记本之间仍可能存在联动问题

- 你明确提到还要覆盖：
  - UI
  - API Key
  - 来源
  - 笔记本
  - Studio
  - Transformations
- 说明这些区域并没有完全收口成一套一致体验。
- 特别是以下问题仍值得继续检查：
  - 模型同步后，页面是否立即刷新
  - API Key 配置后，来源和模型是否同步可见
  - 笔记本打开路径是否与来源/模型配置一致
  - 旧的空状态、遮挡、滚动和导航问题是否彻底清掉

### 5) 代码库历史改动太多，判断成本高

- 当前工作区里有大量历史和并行改动。
- 这会导致两个风险：
  - 看起来“改了很多”，但实际没有击中用户主路径；
  - 某个页面或功能被别的改动无意中影响，导致回归难以定位。

### 6) 文档状态容易误导

- 之前的整改记录和状态文档里出现过“完成”“可用”“已修复”的表述。
- 但用户实际反馈并不支持这些结论。
- 所以现在需要把文档改成更保守的写法：
  - 哪些是已验证通过的
  - 哪些只是局部通过
  - 哪些仍然是风险
  - 哪些只是推断，不是最终确认
